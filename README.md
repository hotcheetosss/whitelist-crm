# WhiteList CRM

REST API для учёта звонков организациям и назначения встреч менеджерам (тестовое задание Б — Software Developer).
Только API, интерфейса нет.

Стек: Python 3.12 (локально подходит 3.11+), FastAPI, pydantic v2, SQLite через стандартный `sqlite3` без ORM, pytest.

## Запуск с нуля

### Вариант 1 — Docker (рекомендуется)

Нужны Docker и Docker Compose.

```bash
git clone https://github.com/hotcheetosss/whitelist-crm.git
cd whitelist-crm
docker compose up --build
```

API: <http://localhost:8000>, интерактивная документация: <http://localhost:8000/docs>.
База создаётся в `./data/crm.db` (папка монтируется в контейнер), миграции применяются автоматически при старте.

Остановить: `Ctrl+C`, затем `docker compose down`. Начать с пустой базы: удалить папку `data`.

### Вариант 2 — без Docker (Python 3.11+)

Linux / macOS:

```bash
git clone https://github.com/hotcheetosss/whitelist-crm.git
cd whitelist-crm
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m app.main
```

Windows (PowerShell):

```powershell
git clone https://github.com/hotcheetosss/whitelist-crm.git
cd whitelist-crm
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m app.main
```

### Переменные окружения

Все необязательные, файл `.env` не нужен.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_PATH` | `./data/crm.db` | путь к файлу SQLite (папка создаётся автоматически) |
| `PORT` | `8000` | порт HTTP-сервера |

Пример (Linux/macOS): `DATABASE_PATH=/tmp/crm.db PORT=9000 .venv/bin/python -m app.main`.

## Тесты

```bash
# в Docker
docker compose run --rm api pytest -q

# локально (после установки зависимостей)
.venv/bin/python -m pytest -q        # Linux / macOS
.venv\Scripts\python -m pytest -q    # Windows
```

Каждый тест работает со своей свежей БД во временной папке, «сейчас» зафиксировано на 2026-11-18 00:00 UTC —
тесты не зависят от реальной даты.

Что проверяют тесты (`tests/`):

| Файл | Что проверяется |
|---|---|
| `test_rules.py` | граница рабочего дня как чистая функция: 09:00 и 17:00 — можно; 08:59, 17:01, 17:30, 18:00, сб, вс — нельзя; перевод UTC → Алматы (в т.ч. переход Казахстана с UTC+6 на UTC+5 в 2024 г.) |
| `test_meetings.py` | пересечение у менеджера (стык 10–11/11–12 — не конфликт; тот же слот, частичное перекрытие с обеих сторон, 1 минута — конфликт); одна активная встреча на организацию (в т.ч. после отмены и после окончания); время без пояса / не целая минута / в прошлом; перенос: `original_starts_at` не меняется, история растёт, перенос в конфликт отклоняется и не меняет встречу; действия над отменённой/начавшейся встречей; append-only история; расписание за день |
| `test_calls.py` | `meeting_set` без встречи / с несуществующей / с чужой / с отменённой встречей; `no_answer`/`refused` со встречей; статус организации = результат последнего звонка |
| `test_companies_and_errors.py` | БИН (дубль — 409, формат — 422), пагинация, единый формат ошибок для 404/405/422, неожиданная ошибка — 500 без внутренностей в ответе |
| `test_concurrency.py` | 8 одновременных запросов на один слот — проходит ровно один (с обычным `BEGIN` вместо `BEGIN IMMEDIATE` этот тест падает — проверено) |

Тесты проверяют не только HTTP-код, но и состояние БД: что после отказа не появилось записей и встреча не изменилась.

## API

Примеры всех запросов — в [`requests.http`](requests.http) (VS Code REST Client / JetBrains HTTP Client);
файл рассчитан на выполнение сверху вниз на пустой базе.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/companies` | добавить организацию: `name`, `bin`, `phone` (необязательный) |
| GET | `/companies?status=&limit=&offset=` | список с фильтром по статусу и пагинацией |
| GET | `/companies/{id}` | организация |
| POST | `/calls` | результат звонка: `company_id`, `result` (`no_answer` / `refused` / `meeting_set`), `meeting_id`, `comment` |
| GET | `/calls?company_id=&limit=&offset=` | звонки (новые сверху) |
| POST | `/managers` | добавить менеджера: `name` |
| GET | `/managers?limit=&offset=` | список менеджеров |
| POST | `/meetings` | назначить встречу: `company_id`, `manager_id`, `starts_at` |
| GET | `/meetings/{id}` | встреча с историей |
| PATCH | `/meetings/{id}` | перенести `{"starts_at": "..."}` **или** отменить `{"status": "cancelled"}` |
| GET | `/managers/{id}/schedule?date=YYYY-MM-DD` | расписание менеджера на день |

### Время

- Принимается ISO 8601 **с часовым поясом** (`2026-11-23T05:00:00Z` или `2026-11-23T10:00:00+05:00`), время без пояса — 422.
- Отдаётся всегда в UTC: `2026-11-23T05:00:00Z`.
- Начало встречи — целая минута. Конец (`ends_at`) вычисляет сервер: начало + 60 минут, клиент его не передаёт.
- Рабочие часы проверяются в `Asia/Almaty` через `zoneinfo`, смещение не захардкожено.

### Ошибки

Все ошибки — в одном формате: `code` — машиночитаемый, `message` — для человека.

```json
{ "error": { "code": "manager_busy", "message": "У менеджера уже есть встреча 23.11.2026 10:00–11:00 (Алматы) в это время", "details": { "meeting_id": 1, "starts_at": "2026-11-23T05:00:00Z", "ends_at": "2026-11-23T06:00:00Z" } } }
```

| HTTP | Когда | `code` |
|---|---|---|
| 422 | невалидное тело/параметры, время без пояса | `validation_error` |
| 422 | вне рабочих часов, в прошлом, перенос на то же время | `outside_working_hours`, `meeting_in_past`, `same_start_time` |
| 422 | звонок `meeting_set` без подходящей встречи / лишний `meeting_id` | `meeting_required`, `meeting_not_found`, `meeting_of_another_company`, `meeting_not_active`, `meeting_not_allowed` |
| 404 | организация, менеджер, встреча, путь не найдены | `company_not_found`, `manager_not_found`, `meeting_not_found`, `not_found` |
| 409 | конфликт с текущим состоянием | `manager_busy`, `company_has_active_meeting`, `duplicate_bin`, `meeting_cancelled`, `meeting_already_started` |
| 500 | неожиданная ошибка (стектрейс только в логе) | `internal_error` |

## Принятые решения (неоднозначности ТЗ)

| Вопрос | Решение |
|---|---|
| Откуда берутся менеджеры | В ТЗ их нет, но без них нельзя назначить встречу — добавлены `POST /managers` и `GET /managers`. |
| Что такое `status` организации | Результат последнего звонка: `new` (звонков ещё не было), `no_answer`, `refused`, `meeting_set`. Отмена встречи статус не меняет — он отражает звонки. |
| «Две активные встречи одновременно» | У организации не больше **одной** активной встречи. Активная = `scheduled` и ещё не закончилась. После отмены или окончания можно назначить новую. |
| Как связан звонок `meeting_set` со встречей | Сначала создаётся встреча (`POST /meetings`), затем звонок с её `meeting_id`. Встреча должна существовать, принадлежать той же организации и быть активной — иначе 422. Для `no_answer`/`refused` `meeting_id` передавать нельзя (422). Несуществующая встреча в звонке — 422 (ошибка валидации по правилу 5 ТЗ), а несуществующие организация/менеджер — 404. |
| Как устроен `PATCH /meetings/{id}` | Одно действие за запрос: `{"starts_at": ...}` — перенос, `{"status": "cancelled"}` — отмена. Оба поля или ни одного — 422. Менеджера и организацию через PATCH не меняем. |
| Что нельзя делать со встречей | Отменённую нельзя перенести или отменить повторно (409). Уже начавшуюся/прошедшую — тоже (409). Перенести на прошедшее время — 422. |
| Перенос | Проходит те же проверки, что и создание (рабочие часы, пересечения, одна активная встреча), исключая саму переносимую встречу: 10:00 → 10:30 у того же менеджера разрешено. |
| История | `original_starts_at` записывается при создании и не меняется. Каждое действие (создана/перенесена/отменена) — строка в `meeting_events` со старым и новым временем; `UPDATE`/`DELETE` в этой таблице запрещены триггерами. История отдаётся в ответе на встречу. |
| За какой день `schedule?date=` | Календарный день по Алматы; время в ответе — UTC; отменённые встречи не включаются. |
| Проверка БИН | Ровно 12 цифр и уникальность. Контрольная сумма не проверяется, чтобы можно было вводить тестовые номера. |
| Пагинация | `limit` (по умолчанию 20, максимум 100) и `offset`; ответ `{items, total, limit, offset}`. |
| Время звонка | Фиксируется сервером в момент запроса; задним числом звонок записать нельзя. |
| Праздники | Не учитываются, только пн–пт. |

## Как устроено

```
app/
  main.py       — создание приложения, обработчики ошибок, подключение роутеров
  config.py     — переменные окружения и бизнес-константы (60 минут, 09–18, Asia/Almaty, лимиты)
  db.py         — подключение, транзакция записи (BEGIN IMMEDIATE), раннер миграций
  deps.py       — зависимости FastAPI: соединение с БД, get_now(), параметры пагинации
  errors.py     — доменные исключения → HTTP-коды
  schemas.py    — pydantic-модели запросов и ответов
  rules.py      — чистые функции: рабочие часы, границы дня по Алматы, форматы времени
  services/     — сценарии и бизнес-правила: companies, managers, meetings, calls
  routers/      — тонкий HTTP-слой
migrations/001_init.sql — схема БД
tests/
requests.http — примеры запросов
```

- Все проверки правил и запись идут **в одной транзакции** `BEGIN IMMEDIATE`: блокировка на запись берётся до проверок,
  поэтому два одновременных запроса на один слот не проходят оба.
- Время в БД хранится строкой `YYYY-MM-DDTHH:MM:SSZ` — у единого формата строковое сравнение совпадает с хронологическим,
  на этом построены SQL-проверки пересечений (интервалы полуоткрытые: `a.start < b.end AND b.start < a.end`).
- Ограничения БД (`UNIQUE(bin)`, `FOREIGN KEY`, `CHECK`, триггеры append-only) — второй рубеж; первый — явные проверки в сервисах.
- Миграции — файлы `migrations/NNN_*.sql`, применяются при старте один раз (учёт в таблице `schema_migrations`).

## Что сделано и что нет

Сделано:

- все эндпоинты из ТЗ + менеджеры и `GET /meetings/{id}`;
- все 7 бизнес-правил, каждое с тестами;
- единый формат ошибок, бизнес-отказы не превращаются в 500;
- запуск через `docker compose up` и через venv, примеры в `requests.http`.

Не сделано / известные ограничения:

- Если блокировка SQLite не освободится за 5 секунд (`busy_timeout`), запрос завершится 500, а не понятным 503 —
  при нагрузке одного API-процесса это маловероятно, но не обработано.
- Нет редактирования/удаления организаций и менеджеров, нет списка всех встреч с фильтрами — в ТЗ не требовалось.
- Праздники и переносы рабочих дней не учитываются.
- Числовая метка времени (unix timestamp) в `starts_at` принимается pydantic как UTC — не запрещено отдельно.
